# Status, 2026-10-17: nearly stable (update to 2026-10-16)

A plain progress report for the Windows/WHPX port of reims-vgpu, one day after
`STATUS-2026-10-16.md`. It covers this tree (the two newest commits only add
this report and repoint `.gitmodules`) paired with the `vendor/qemu` commit it
pins. What changed since 10-16 is a build-level change (PGO), per-host default
values, one bug fix (stalled guest sockets) and a number of opt-in experiments
that are off by default. That file stays in the tree for the record; where the
two differ, this one wins.

Numbers come from our lab queues (`bNNN`, `nNNN`) on one machine: Intel
i7-14700K, RTX 4060, Windows 11 with WHPX, macOS Tahoe at 5120x2160 and 240 Hz,
24 vCPUs. Each queue alternates its arms (A, B, A, B), because the guest drifts
from one queue to the next; compare arms inside a queue only, never a number
from one queue with a number from another. They are not a benchmark of anyone
else's hardware.

## Changed since 2026-10-16

- **Profile-guided optimization, retrained.** Our builds use PGO on both
  sides: LLVM PGO for the Rust crates and gcc PGO for the C side of
  `vendor/qemu`. The Rust profile we had been using dated from 2026-10-12 and
  was stale: the build logs showed dozens of "hash mismatch" lines, so hot
  functions were compiled without a profile. Retrained on the current tree:
  - b670 (ABAB): Apple Maps 49.2 against 43.5 fps (+13 %), Safari
    canvas about 69 against 61-67 fps.
  - b672 (ABAB): the gcc PGO of the QEMU C side on top of the retrained Rust
    profile: Maps 51.9 against 47.7 fps (+9 %). Against the 10-16 build the
    two steps together are +19 % on Maps (43.5 to 51.9) and canvas goes from
    61-67 to about 69.
  - The 10-16 build carried the stale profile, so these figures are not a
    comparison against an unprofiled build; we did not measure that.
  - How to build with PGO is specific to our environment (compiler versions,
    profile training runs on our guest workload). The profile files are not
    part of this repository and would not match another tree anyway. A plain
    release build works and is simply slower.
- **Safari caps page rendering near 60 fps** unless the WebKit preference
  `PreferPageRenderingUpdatesNear60FPSEnabled` is switched off in the guest.
  Canvas figures above 60 fps need it off; this is a guest setting, not a
  device limit.
- **Per-host defaults in one executable.** The fast MMIO compare path
  (`QEMU_WHPX_MMIO_FAST_CMP`) is off by default on Intel and on elsewhere: on
  an AMD host it was fps-equal with less BQL wait, and a twin of it lost 4-45 %
  of the 5K canvas on Intel (b644 and an Intel queue of our second agent).
  `DIRTY_WP_HASHED` (write-protect hashed sets that keep syncing clean) is on
  for every host: on the AMD host it measured canvas +35 % and Maps +20 %
  (b636-b647, 9 boots). The CPU vendor stands for a
  measured split, not a model-level one; other CPUs may want other values (see
  `reims-dirty-hash-config` in the QEMU log and the `REIMS_VGPU_LAB_DIRTY_*`
  overrides).
- **`FD_SETSIZE` is 1024 on Windows** (`vendor/qemu`, `include/qemu/osdep.h`).
  QEMU's main loop polls sockets through `select()`, and winsock's `FD_SET`
  silently ignores a socket once 64 are set. With `-netdev user` every guest
  TCP connection is one host socket, so past 64 open connections the newest
  were never polled and new sites stalled in the guest browser.
- **USB passthrough helper keep list** (host-side tooling, not in this
  repository): a USB audio device that Windows itself uses for sound must stay
  with Windows and is no longer handed to the guest.

## Tried and did not win (opt-in, off by default)

- **`REIMS_VGPU_LAB_BUF_RESIDENT=on`**: keeps a buffer window's staging copy
  while a witness (guest-write generation, host writes, strided audit) says the
  bytes did not change. It targets the finding that 89-91 % of the Maps lane
  copy bytes repeat the previous copy (b653). It showed no gain; it stays as a
  switch.
- **Guest-RAM import (`GUEST_IMPORT`) with any combination of write/read
  narrowing is a loss on Intel with a discrete GPU.** n363 (ABAB), Maps
  17.7-18.2 fps against 45.9 with the import off; canvas 57.9-59.2 against
  61.2-63.3. The 10-16 report had the same verdict from another angle (b626).
  The import stays off by default here. It may pay on an iGPU, a unified-memory
  host or another discrete GPU; we have no measurement of those.

Other lab switches merged in this range, all off by default and not
recommended yet: `IRQ_URGENT` (a drained ring's lone EXEC word skips the interrupt
batch hold), `WALK_XMEMO` (resolve answers kept for a doorbell batch), a census of
returning IOSurfaces on map/unmap, and `GUEST_IMPORT_READS` narrowing.

## New opt-in: `REIMS_VGPU_LAB_PRESENT_SHARP=on`

A Catmull-Rom (bicubic) scaled present in the host window, for a guest mode
below the panel's native size (for example 4608x1944 on a 5120x2160 screen,
text about 11 % larger). Without it the aspect-fit blit filters linearly and
softens glyph edges. It is for non-native modes only; at native size the
window needs no resample, and we do not enable it by default.

## Still open (unchanged from 2026-10-16 unless noted)

1. Safari canvas is bound by the guest (one WebKit GPU-process thread at about
   99.7 % of a core); we have no host-side lever yet.
2. A fresh macOS needs `METAL_ERROR_MODE=3` in the Data volume's global
   preferences; the root fix belongs in the guest driver patch.
3. USB and Bluetooth passthrough is host-specific lab work and not a feature
   of this branch.
4. About 1,450 `TEMP lab` markers and over 250 `REIMS_VGPU_LAB_*` variables are
   still lab scaffolding. All diagnostics are off by default.
5. Windows page aliases (one view per RAM page, or per run of pages) stay off
   by default (`QEMU_WIN_PAGE_ALIAS=on` to experiment). A per-run variant is in
   the tree, but we have seen boots where `MapViewOfFile3` took milliseconds
   per call under the BQL, so we do not recommend it.

## Reproducing and contributing

`.gitmodules` points `vendor/qemu` at `MAXZVER/qemu-reims-vgpu`, branch
`windows-2026-10-17`, so

    git clone --recurse-submodules --branch windows-2026-10-17 \
        https://github.com/MAXZVER/reims-vgpu.git

resolves. Windows needs a build of the pinned QEMU with WHPX; the rest is as in
`README.md`.

If you propose a change, please base it on `windows-2026-10-17`, keep it to one
concern, and send a before/after from one boot (arms alternated). Reports from
other hardware are valuable precisely because ours is one Intel plus RTX 4060
machine and one AMD desktop; say what CPU and GPU you ran. The default values
of the dirty-page hashing in particular were tuned on those two.
