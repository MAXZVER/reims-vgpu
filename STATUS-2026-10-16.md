# Status, 2026-10-16: nearly stable

This is a plain progress report for the Windows/WHPX port of reims-vgpu. It
covers the build at `90015adb` (this repository) paired with `vendor/qemu` at
`4aefb2c1`. Numbers come from our lab queues, cited as `bNNN`; each queue
alternates its arms inside one guest boot because the guest drifts between
boots. Numbers are from one machine and are not a benchmark of anyone else's.

## What runs today

macOS Tahoe 26 as a guest on Windows 11 with WHPX, at 5120x2160 and 240 Hz,
24 vCPUs, host GPU RTX 4060 (Intel i7-14700K host). Vulkan device selection,
Metal-to-Vulkan translation and the QEMU device are all in this tree.

Measured on the default configuration after the fixes below
(b624-b628, queues of 2026-10-16):

| Scene | Result | Queue |
| --- | --- | --- |
| Safari, 5K canvas | 66-68 fps | b610, b624, b626 |
| Apple Maps | 46-53 fps | b624, b626 |
| Glass scroll (Safari) | 190-207 Hz | b610, b624, b626 |
| Continuous 5K Finder drag | 160-166 Hz | b607 |

The canvas figure is bimodal by boot (61 or 68 fps, b613); we quote the range.

## Fixed on 2026-10-16

- **Electron/Chromium stale tiles** (Claude.app, any Chromium app that rasters
  with Skia Graphite). Tiles stayed wrong permanently after a window resize:
  glyphs, button backgrounds and rounded-rect masks vanished at tile seams.
  Cause: this device executes blits on the CPU straight into guest pages while
  it walks the command stream, but earlier recorded draws read the same atlas
  from guest RAM only when the GPU runs them, so the blit overwrote rows that a
  draw had not read yet. Fix: draw preparation names every (task, reference)
  that a recorded draw reads from guest RAM, and a CPU blit or CPU mipmap chain
  into such a reference first waits for the recorded GPU work
  (`runtime::inflight_reads`, commit "Order host-side blits after the recorded
  draws that still read them"). The names are resolved against submission
  watermarks (commit "Resolve in-flight guest reads against submission
  watermarks") so a write whose reads have already executed does not wait: 0
  waits in the Claude.app check queues instead of about 44 per second. Checks:
  b600-b602 clean 3/3; interleaved A/B b603-b606 (fix off: stale, on: clean);
  Claude.app checks b612, b615, b617, b618, b623, b625 clean; no measurable
  cost on Safari scroll.
- **Maps regression** (Maps 44-52 fps down to about 20 fps between our build of
  2026-10-15 11:46 and the builds of 2026-10-16 morning) Bisected over b616-b619 to a change that kept the
  draw pool's parallel jobs from reading the sampled-source resolve memo, so
  every job re-resolved what the drain had resolved for it. The memo is now
  stream-wide and invalidated by every writer in stream order (pass
  attachments, blit destinations, mipmap chains, compute storage images)
  (commit "Keep the resolve memo for the stream and let every writer invalidate
  it"). b624: Maps 46.2/52.9, canvas 68.1, scroll 207 Hz, at parity with the
  earlier fast build.
- **QEMU abort on 64-bit `bt`/`bts`** in the x86 emulator: the REX prefix was
  refused, so one guest instruction on emulated memory killed the VM with
  `0xc0000409` (b608). Fixed in `vendor/qemu` (`4ed70c31`).
- **Windows packed page aliases are now off by default.** The aliases (one
  `MapViewOfFile3` placeholder view per 4 KiB page, `6e425e43`) made heavy
  WebKit unusable: 5K Safari canvas 0.4 fps, scroll 6.6 Hz, vCPUs stuck out of
  the hypervisor for more than a second (b609, b610). Off: canvas 61-68 fps,
  scroll 190-203 Hz. `QEMU_WIN_PAGE_ALIAS=on` re-enables them for A/B
  (`4aefb2c1`).

## Earlier in this series

- virtio-sound with a device-side jitter buffer (120 ms default): 0 gaps against
  5 for usb-audio over the same run (b459).
- Write-protection based dirty tracking (`DIRTY_WP`) as the default harvest on
  WHPX, with the hypervisor view's page protection (`WP_VIEW`) and the bridge
  for queried sets (b453: canvas +27 %, Maps +8 %, no artifacts).
- Decode of Metal render opcodes 0x1d/0x1c (indexed base-vertex draws), native
  RGBA32Float and R16Float rails, MSAA sample-count specialisation and a
  demotion rail for sampling single-sample content through a multisampled bind.
- A zero-errors audit of the always-on failure channel: diagnostics moved to an
  off-by-default channel, real losses fixed.

## Open problems

1. **Safari canvas is bound by the guest.** The device keeps up with what the
   guest issues: the swap is processed 0.11 ms after it arrives and completion
   stamps wait about 0.7 ms (b626, b624). The frame (14.6 ms) is paced by one
   WebKit GPU-process thread at 99.7 % of a core inside the guest, plus waits
   on command-buffer completion (b627: about 214 command buffers per frame,
   two running WebKit threads, WindowServer 59 %). We have not found a host-side
   lever yet.
2. **Guest-RAM import for GPU reads is a loss on a discrete GPU.** With
   `GUEST_IMPORT=on` and surface writes narrowed: scroll 39 Hz, canvas 19 fps
   against 190-207 Hz and 66-68 fps on the copying rails; drain duty 0.89
   (b626, RTX 4060: the GPU gathers guest pages over PCIe). We keep the import
   off by default on this host class. It may still pay on an iGPU or
   unified-memory host; we have no measurement for that.
3. **A fresh macOS needs `METAL_ERROR_MODE=3`** in the global preferences of the
   Data volume, because the device reports no Metal target architecture. We
   write it from the recovery terminal before first boot. The root fix belongs
   in the guest driver patch and is pending.
4. **USB and Bluetooth passthrough is host-specific lab work** (adapter reset,
   xHCI changes in `vendor/qemu`). It is not ready to be called a feature of the
   public branch.
5. **Many `TEMP lab` switches remain.** About 1,450 `TEMP lab` markers in 112
   files and over 250 `REIMS_VGPU_LAB_*` variables. All diagnostics are off by
   default, but they are lab scaffolding that has not been consolidated, and
   some probes write to hard-coded paths such as `E:/tmp-c/tiledump` (only
   when switched on).
6. **Residual intermittence.** Claude.app has been clean in 6 consecutive checks
   on the final code, but earlier "clean" runs of this bug turned out to be
   luck (b529), so we call it fixed, not closed. Known limit of the fix: the
   ordering is keyed by reference, so a write through a view of a texture read
   under another name is not ordered (none seen).
7. Three `buffer_plan` unit tests fail only when run in the same process as the
   draw/exec tests (order dependent, pass alone 7/7, same on the previous
   head); one `blit_exec` test races a shared counter when run in parallel.

## Reproducing

`vendor/qemu` must be taken from the branch published next to this one; the
submodule URL in `.gitmodules` still points to the upstream repository, which
does not contain commit `4aefb2c1`. Build and run instructions are unchanged
from `README.md`; Windows needs a build of the pinned QEMU with WHPX.
